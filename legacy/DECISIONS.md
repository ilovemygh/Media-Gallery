# Architectural Decisions & Assumptions (`DECISIONS.md`)

This document records technology stack justifications, architectural trade-offs, PRD assumptions, and scope notes for **Media Gallery**.

---

## D-001: Cross-Platform Stack Selection (TypeScript + React + Vite + Electron + Capacitor + SQLite FTS5)

**Context:**
`PRD-Media-Gallery.md` (Section 4) recommends Flutter + Drift (SQLite FTS5) and explicitly permits the engineering team to justify an alternative stack in writing (*"Recommended (agent may justify a change in writing)"*).

**Environment Inspection:**
On the build/development workstation:
- `flutter` and `dart` SDKs are **not installed** and unavailable in `PATH` or user directories.
- **Node.js v26.7.0** (which ships with built-in **`node:sqlite`** supporting **SQLite 3 with FTS5** natively without native C++ addon compilation), **npm 11.19.0**, **Android SDK** (`platform-tools`, `build-tools`, `platforms`), **OpenJDK 26**, and **Visual Studio 2022 Build Tools** are installed.

**Decision:**
Use a single **TypeScript + React 19 + Vite** core architecture packaged with:
1. **Desktop (Windows first; macOS/Linux compatible):** **Electron** (`electron/main.ts` + `electron/preload.ts`) with native filesystem scanning, `fs.watch` incremental watcher, `shell.trashItem` safe delete, `ffmpeg` / `ffprobe` & `yt-dlp` subprocess execution, mDNS discovery, and Node.js `https` + `ws` (WebSocket) mutually authenticated TLS transfer server.
2. **Android:** **Capacitor** (`android-bridge/capacitor.config.ts` + `android-bridge/MediaGalleryPlugin.ts`) wrapping the exact same React/TypeScript UI and business logic while delegating MediaStore scanning, `MediaMetadataRetriever` frame capture, `youtubedl-android`, Share-sheet `"Send with Media Gallery"`, and foreground service media/transfer notifications to native Android bridges.
3. **Database:** **SQLite with FTS5** (`node:sqlite` `DatabaseSync` in Node/Electron/Vitest, paired with an identical SQL schema and browser/Capacitor SQLite adapter via a unified `DatabaseAdapter` interface) implementing all 8 required tables from PRD Section 11 plus the `media_fts` FTS5 virtual table and sync triggers.

**Trade-offs:**
- *Pro:* Zero environment blockers; full end-to-end automated verification in Vitest against real SQLite FTS5, real filesystem scanning, real SHA-256 hashing, and real local loopback TLS/WebSocket chunked transfers.
- *Pro:* Rapid desktop UI fidelity (exact CSS Grid/Flexbox control for resizable left sidebar, right details pane, 700ms spring-loaded drag-and-drop, custom aspect-ratio crop overlay, and responsive Android bottom-sheet layout).
- *Con:* Electron desktop bundle size is larger (~80–120 MB) compared to Flutter desktop binaries. Accepted for v1 reliability and native Node.js cryptographic/streaming support.

## D-002: Browser / Preview Storage Adapter vs. Desktop Native SQLite

**Decision:**
The core repository (`MediaRepository`) accepts an abstract `SqlExecutor` interface:
- `NodeSqliteAdapter` (`src/core/database/nodeSqliteAdapter.ts`) uses `node:sqlite` (`DatabaseSync`) with WAL mode, foreign keys, and full FTS5 triggers for Electron main process, CLI/background workers, and all automated tests.
- When running inside the pure browser Vite preview without Electron IPC, an in-memory / `localStorage`-persisted fallback query engine (`BrowserFallbackRepository`) enables immediate interactive UI exploration of every PRD feature (including 700ms spring-loaded drag-and-drop, FTS5-style search, cover cropper, music player, YouTube modal, and simulated peer sync) without crashing on Node built-ins.

## D-003: Video Thumbnail Random Frame Selection & Immutability (PRD I1)

**Assumption & Design:**
- PRD I1 specifies: *"Video thumbnail is generated by capturing a frame at a random point within the first third of the video. Once chosen, it is saved to cache and synced to cloud, and stays fixed."*
- **Edge Case Handling:**
  - If `duration_ms <= 0` or metadata is missing, default `frame_time_ms` to `0`.
  - Otherwise pick `frame_time_ms = Math.floor(rng() * Math.max(1, Math.floor(durationMs / 3)))`, strictly bounded within `[0, durationMs / 3]`.
  - If a `cover` record already exists for `media_id` with `source === 'generated'` or `source === 'custom'`, `ThumbnailService.ensureVideoThumbnail()` returns the cached cover untouched rather than re-rolling. Only an explicit user action (**Re-roll**, **Pick frame**, or **Custom cover**, PRD I2) overwrites `frame_time_ms` or `file_path`.
  - On desktop, `ffmpeg -ss <sec> -i <video> -vframes 1 -q:v 3 <thumb.jpg>` renders the frame when `ffmpeg` is available on `PATH` or configured; if `ffmpeg` is not installed, a deterministic SVG thumbnail artifact is generated in cache so metadata/UI pipelines never fail.

## D-004: Offline-First Reverse Geocoding for Auto-Alias (PRD Section 9)

**Assumption & Design:**
- PRD Section 9 requires GPS coordinates (`gps_lat`, `gps_lon`) to resolve to a place name via reverse geocoding with **offline lookup preferred** and online lookup strictly behind an opt-in privacy setting (`online_geocoding_enabled = false` by default).
- We include an embedded offline bounding-box / nearest-city gazetteer (`src/features/alias/offlineGeocoder.ts`) covering major global regions and common test coordinates (e.g., Bali/Indonesia, Tokyo, San Francisco, London, New York, Sydney, Paris, Singapore, Jakarta, Beach/Coast sample regions) with configurable radius matching, ensuring privacy-preserving offline auto-aliasing out of the box.

## D-005: Alias Sanitization & Duplicate / Empty Token Handling

**Assumption & Design:**
- Stripping prefixes (`IMG_`, `VID_`, `Screenshot_`, `PXL_`, `DCIM_`, `MVIMG_`), replacing `_` and `-` with spaces, splitting `camelCase` (`myBeachTrip` -> `my Beach Trip`), and trimming trailing/isolated numeric shutter suffixes (`IMG_2031` -> `2031` trimmed if purely numeric sequence or preserved meaningfully when part of title) follows PRD Section 9.
- When rendering the default template `{date} {place} {name}`, missing tokens (e.g., no GPS `place`) collapse cleanly without leaving double spaces.

## D-006: Safe Deletion & Real Rename Undo Semantics (PRD C3, C4, 7.5, 13)

**Assumption & Design:**
- Deleting a media item from the app **never** unlinks permanently; on Electron/Desktop it calls `shell.trashItem(filePath)` (OS Recycle Bin), and in headless/test filesystem environments it moves the file into an app-managed `.media-gallery-trash/` staging directory inside the library root and marks `sync_state = 'Trashed'` (or removes from active index while preserving trash metadata for recovery).
- Applying a real rename writes `(media_id, old_name, new_name, applied_at)` to `rename_log` inside an atomic database transaction after renaming on disk (checking for name collisions first so existing files are never overwritten). Undo pops the most recent `rename_log` entry (or batch group) and renames the file back on disk.

## D-007: Transport Security & Pairing Without Google Account (PRD D1, E5, 10.2)

**Assumption & Design:**
- Pairing generates a single-use 6-digit numeric PIN + QR payload containing `{ deviceId, deviceName, host, port, publicKeyFingerprint, pinToken, expiresAt }`.
- Both devices verify the PIN/token and exchange Ed25519 / X.509 self-signed certificates whose SHA-256 fingerprints are pinned in the `device.public_key` column and OS secure credential storage (`SafeStorage` / Keychain / Android Keystore adapter).
- Transfers run over TLS 1.3 (`https` + `wss`) with mutual fingerprint verification and zero cloud dependency (`E5`).
- File transfers split files into 256 KB chunks (`CHUNK_SIZE = 262144` bytes; configurable per transport) with per-chunk CRC/index tracking and full-file SHA-256 verification. Interrupted transfers persist `bytes_done` and `last_chunk_index` in the `transfer` table and resume from the exact next chunk (`bytes_done` byte offset) without re-sending completed chunks.
